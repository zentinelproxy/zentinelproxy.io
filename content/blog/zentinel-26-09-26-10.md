Between 1 September and 18 October we shipped nine releases, 26.09_1 through
26.10_3 (crate versions 0.6.38 to 0.6.46). Some of them add things. More of them
fix things that looked like they worked and did not, and those are the ones this
post spends most of its time on, because they are the ones that change what your
deployment was actually doing.

If you only read one section, read the next one.

## Health checks never probed anything (26.09_2)

On 0.6.38 and earlier, every `health-check` block in every configuration was
inert. The active health checker built its backend set from the configured
targets but never populated the set that the probe loop iterates, so every cycle
checked zero backends — for `http`, `tcp`, `grpc` and `inference` checks alike.

It failed silently in both directions. No probe was sent, so a backend that was
down was never detected; and no backend was ever marked unhealthy, so nothing was
ever taken out of rotation. The runner started, logged that it had started, and
ticked on schedule, while the configuration and `zentinel lint` both reported
health checking as configured. Measured against a real backend at
`interval-secs 2`: 0 probes in twelve seconds before the fix, 29 after.

Anyone relying on health-checked failover did not have it. No configuration
change is needed: existing `health-check` blocks start working on upgrade.
**That also means backends that have been failing quietly may be marked unhealthy
and removed from rotation for the first time.** Check which backends are marked
unhealthy after upgrading rather than assuming nothing moved.

## Agents: sockets, restarts and installs

Three separate faults, each of which made agents appear to do nothing rather than
produce an error — and with `failure-mode "open"`, the default in the shipped
examples, traffic flowed unprocessed.

**Container images could not create agent sockets (26.09_3).** `/var/run/zentinel`
was not created in any image, so a Docker named volume mounted there came up
root-owned while the agent images run as `nonroot`. The bind failed, the proxy
had nothing to connect to, and every agent route failed open. The images now
create the directory, but because `/var/run` is a symlink to `/run` on both the
Debian and distroless bases, that is not a reliable fix on its own. If you write
your own Compose file, prepare the volume explicitly with an init container (the
shipped `docker-compose.yml` shows how, with mode `1777`).

**An agent the proxy could not reach at startup was lost until the proxy
restarted (26.09_4).** That covered an agent slower to start than the proxy, an
agent on a volume that was not ready yet, and any agent that *restarts* — a
crash, an upgrade, a rolling deploy. Four things had to change: unreachable
agents are now registered and marked unhealthy instead of refused, pool
maintenance starts independently of registration, reconnection no longer gives
up after three attempts (the attempt count now bounds the retry interval, capped
at two minutes), and a reconnected agent's capabilities are re-learned. If you
added start-ordering to work around this, it is no longer required.

**`zentinel bundle install` failed for every non-root user (26.09_5).** The
writability check asked "can anyone write here?" instead of "can I?", so
`/usr/local/bin` looked writable to everyone, the installer chose a system-wide
install, and then failed creating `/etc/zentinel/agents`. It now uses `access(2)`
on every directory the install creates. A user-local install goes to
`~/.local/bin` and `~/.config/zentinel/agents/`; use `--prefix` to choose
somewhere else. Reported by [@alanorth](https://github.com/alanorth), who also
noticed the registry pages named a path the installer has never used; all 23
agent pages were corrected.

## MCP gateway

The MCP work in 26.09_2 is covered in
[A Gateway for Agentic Protocols](@/blog/the-gateway-for-agentic-protocols.md):
per-tool metrics (`zentinel_mcp_calls_total`, resolved from the body and bounded
by the route's configuration), per-tool rate limiting via the `mcp-tool` and
`client-ip-and-mcp-tool` keys, `tools/list` filtered to what the route permits,
and an MCP-native `health-check { type "mcp" }`.

Since then:

- **One route can front several MCP servers as a single endpoint (26.09_3).**
  `tools/list` merges every upstream's tools under a declared prefix, and a call
  is routed by that prefix. A `session-key` is required with two or more
  upstreams, and policy applies to the name the client sees
  (`deny "warehouse.execute_sql"`). An unreachable upstream costs its own tools
  in the listing and no others. Resources are refused on a multiplexing route,
  because a URI cannot carry an upstream prefix.
- **JSON-RPC response ids keep their type (26.09_3).** `"id": 42` had been
  answered as `"id": "42"`.
- **Multiplexed tool calls are proxied rather than originated (26.09_4)**, so
  they now use the connection pool, the route's retry policy and the upstream's
  TLS settings. Listings and the per-upstream `initialize` handshake are still
  composed by the proxy.

The configuration reference is in the
[agentic protocols docs](https://docs.zentinelproxy.io/configuration/agentic/).

## Pingora 0.9.0 (26.09_6)

The engine under Zentinel moved from Pingora 0.8.1 to
[0.9.0](https://github.com/cloudflare/pingora/releases/tag/0.9.0); our fork was
rebased in [zentinelproxy/pingora#10](https://github.com/zentinelproxy/pingora/pull/10)
and both fork patches carry over unchanged in behaviour. What it brings:

- Request-target hardening: path and authority validation share one parser,
  ambiguous authorities are rejected on ingress and egress, and CR/LF in an
  HTTP/2 `:path` is rejected.
- Hop-by-hop request headers are stripped before the upstream sees them, along
  with any header the client nominates in `Connection`. A request that nominates
  `Host`, a forwarding header or a pseudo-header-shaped name is rejected.
- HTTP/1 upstream connections are never reused after an incomplete response or a
  failed write.
- Default HTTP/2 server limits are bounded rather than unbounded.

One forwarding behaviour changes and is worth checking before you upgrade:
**WebSocket upgrades still work, but other HTTP/1 upgrades (for example `h2c`)
are no longer forwarded**, and `Proxy-Authorization` is not passed on. Nothing in
the configuration turns the old pass-through back on; if you depended on it,
[open an issue](https://github.com/zentinelproxy/zentinel/issues). Cache keys
and on-disk hashes are unchanged, so no cache goes cold.

## ACME: renew when the CA suggests (26.10_2)

When the ACME server supports ACME Renewal Information
([RFC 9773](https://www.rfc-editor.org/rfc/rfc9773)) — Let's Encrypt does —
Zentinel now asks the CA for its suggested renewal window and renews at a
uniformly random point inside it, so a fleet does not renew at the same moment.
`renew-before-days` stays a hard floor: ARI can make a renewal earlier, never
later. Renewal orders also name the certificate they replace, which at Let's
Encrypt exempts the renewal from rate limits. CAs without ARI behave as before.
No configuration change is needed. Thanks to
[@Curious-r](https://github.com/Curious-r) for this and the Cloudflare fix below.
See [the ACME docs](https://docs.zentinelproxy.io/configuration/listeners/#ca-suggested-renewal-windows-ari).

## Security and dependency sweep (26.09_1 to 26.10_3)

26.10_3 is mostly security updates in dependencies. Nothing in it changes how
Zentinel routes, inspects or blocks traffic.

- **`wasmtime` 48.0.0 → 49.0.3** for WASM agents: 23 advisories
  (RUSTSEC-2026-0314 to -0364), including a critical native stack buffer
  overflow (RUSTSEC-2026-0327) and a WASI filesystem sandbox escape
  (RUSTSEC-2026-0352). Only relevant if you run WASM agents.
- **`rustls` 0.23.46** (RUSTSEC-2026-0346 to -0349), mostly in rustls as a TLS
  client — the role Zentinel has toward upstreams, agents and the ACME server.
  26.10_1 had already taken 0.23.45, with stricter handling after a
  HelloRetryRequest.
- **`h2` 0.3.27 is gone** from the tree (RUSTSEC-2026-0258), and
  `crossbeam-epoch` moves to 0.9.21 (RUSTSEC-2026-0204). `cargo audit` is clean.
- **OpenTelemetry 0.33**, with no code changes needed.
- **`maxminddb` 0.32 (26.10_1)** bounds the work done decoding a crafted GeoIP
  database. The database is operator-supplied, so this matters only if its
  source is not fully trusted.

26.10_3 also fixes **Cloudflare DNS-01 for subdomains**: the provider looked up
only a zone named exactly like the certificate's domain, so `app.example.com`
could not be issued when the zone is `example.com`. It now walks up to the most
specific parent zone that exists, and still reports API and authentication
errors as errors.

**Building from source now needs Rust 1.96**, required by `wasmtime` 49.
Prebuilt binaries and container images are not affected.

## Upgrading

No release in this range needs a configuration change. Two things deserve a look
afterwards:

1. **Upstream health.** If you configure `health-check`, backends may be marked
   unhealthy for the first time.
2. **Non-WebSocket upgrades.** If any client relies on `Upgrade: h2c` or similar
   being forwarded, it no longer is.

The full detail, including everything we left out here, is in the
[CHANGELOG](https://github.com/zentinelproxy/zentinel/blob/main/CHANGELOG.md),
and the general procedure is in the
[upgrade guide](https://docs.zentinelproxy.io/operations/upgrade-guide/).
